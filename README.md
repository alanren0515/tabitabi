# TabiTabi MVP

日本餐厅行动助手的移动优先 Web/PWA 原型。它实现了 PRD 中最小闭环：输入文字或截图、审阅截图提取结果、确认候选、查看预约或排队建议、复制电话话术、保存想去清单。

安装为 PWA 后，在支持 Web Share Target 的设备和浏览器上，可以从 TikTok、Instagram、X 或普通浏览器的系统分享菜单把标题、文字和链接直接送到 TabiTabi。分享内容只会预填输入框，不会自动分析；页面会立即从地址栏移除分享参数，用户检查并点击“开始分析”后才发送请求。图片分享暂不接管，截图仍通过页面上传。

Service Worker 只预缓存应用外壳（HTML、前端模块、样式、manifest 和图标），不缓存 `/api` 响应、餐厅结果、分享参数或任何第三方页面。离线时可以打开界面并查看本机保存的计划、待分析队列和历史；新的截图识别、餐厅搜索、评分预览与官网核对需要联网。

## 本地运行

随时运行 `npm run status` 可得到不含任何 Key 的当前配置、评估进度、剩余外部证据和下一条命令。它会直接读取当前隐私最小化事件日志计算 live 输入与反馈数量，不再依赖上一次生成的 pilot 报告；自动测试、release gate 和 pilot gate 仍分别承担各自的验证职责。

```bash
npm run dev
```

然后打开 `http://localhost:4173`。

### 启用任意截图理解

不配置 API key 时，用户本次提供的 TikTok 示例截图仍可通过本地示例数据跑通完整流程。要处理任意截图：

```bash
cp .env.example .env.local
```

默认视觉架构是 Qwen3-VL-Flash 主模型、GPT-5.4 mini 质量兜底。然后在 `.env.local` 中设置：

```text
DASHSCOPE_API_KEY=your_dashscope_key
OPENAI_API_KEY=your_key_here
GOOGLE_MAPS_API_KEY=your_google_maps_key
HOTPEPPER_API_KEY=your_hotpepper_key
```

完整配置项和新加坡区域 endpoint 见 `.env.example`。只配置 Qwen 或只配置 OpenAI 也能运行；两者都配置时调用顺序为：

1. Qwen3-VL-Flash 读取截图并返回 JSON Mode；一张图最多提取 6 家明确可见的餐厅。
2. 服务端严格按统一 JSON Schema 校验，不把供应商承诺当作校验结果。
3. Qwen 超时、限流、鉴权失败、空输出、非法 JSON、Schema 不符、低置信度或缺少关键餐厅线索时，调用 GPT-5.4 mini。
4. 两个模型结果都较弱时保留更安全的结果，并要求用户确认，不会把低置信度伪装成成功识别。

API key 只保存在服务端环境中，不会发送到浏览器。截图仅在当前请求内处理，不写入磁盘。日志只记录供应商、模型、耗时、状态和 token 使用量，不记录图片、OCR 全文、提示词或餐厅信息。

真实餐厅核对采用两阶段请求：

1. 候选搜索只请求 Place ID、店名、地址、类型、营业状态和地图链接。
2. 用户确认后才进入完整餐厅核对并匹配 Hot Pepper；若用户在候选页主动点击“按需查看评分”，会提前请求该候选的 Place Details，但只返回评分预览，并在随后确认时复用同一份短缓存结果。

浏览器保存清单时不会长期保存 Google Places 返回的完整内容，只保存 Place ID、用户自己的线索和状态；重新打开时刷新详情。

### 当前 API

```text
GET  /api/capabilities
POST /api/extract-screenshot
POST /api/extract-text
POST /api/extract-webpage
POST /api/restaurants/search
POST /api/restaurants/candidate-preview
POST /api/restaurants/details
POST /api/events
```

`/api/events` 记录输入类型、识别成功、候选确认、候选评分预览、分析完成、预约/电话/话术行动、来源冲突、保存计划状态和用户主动提交的反馈。每次新分析只附带一个短期、随机的 `analysisRunId`，用于把同一次流程里的重复点击去重；它不是用户 ID。审计工作台打开的主产品页会标记 `trafficType=audit`，不会进入真实试用指标。分析耗时定义为“确认候选到行动建议出现”，上限 5 分钟；历史/清单刷新不计作新分析。事件不记录截图、原始搜索输入、具体用餐日期、评分值或第三方餐厅详情。反馈可包含用户主动填写的最多 500 字说明。开发环境写入 `data/events.jsonl`，该文件已被 Git 忽略。

如果同一次分析的任何阶段使用本地演示或已知样例回退，该 `analysisRunId` 的所有事件都会从真实 pilot 指标中排除；后续即使调用了实时 Places，也不会把“半演示”流程误算成真实样本。

从多餐厅截图或旅行清单的“待分析队列”打开一家店时，会建立新的分析运行并独立计算完成与行动；重新打开最近分析或想去清单只刷新信息，不建立新运行，也不会把后续点击归到上一家餐厅。

数据源调用的阶段、字段费用层级、耗时、成功状态和候选数量写入 `data/source-metrics.jsonl`；视觉调用还记录输入、输出、图片和总 token。不会记录查询文字、截图或 API key。`npm run metrics:summary` 会汇总行动率、候选评分加载率、确认后平均/p95 分析耗时、30 秒内完成率、错误率、fallback 次数和平均 token，实际费用仍以供应商账单为准。漏斗与 pilot gate 共用合格 live 运行口径：按 `analysisRunId` 去重，排除审计、旧版及任何混合 demo 运行；同一结果重复点击不会让行动率超过 100%。

设置页会显示日本时间当天的截图识别、Places 搜索和 Places 详情应用预算。该状态只包含用量、上限与剩余额度，不返回 API Key；缓存命中不扣额度，每次实际进入供应商调用前也会在响应头 `X-Daily-Budget-Remaining` 返回对应预算桶的剩余次数。

前端对能力状态采用一分钟成功缓存和五秒失败缓存。临时网络或 `/api/capabilities` 错误会显示“状态暂时不可用”，不会被误报成 API 未配置或静默进入演示候选；恢复联网、进入设置页或点击刷新都会重新核对。PWA 离线壳只缓存静态模块，不缓存任何能力、预算或餐厅 API 响应。

Google Places 搜索和详情请求使用 60 秒服务端短缓存，并合并同时发生的相同请求，减少重复点击、评分预览、页面刷新和并发请求造成的重复计费；候选评分预览与确认详情共用同一缓存，指标中的 `cacheStatus` 会标记 `miss`、`hit` 或 `coalesced`。

昂贵接口按客户端 IP 进行固定窗口限流：截图识别每分钟 10 次，Places 搜索和详情各每分钟 30 次。部署在可信反向代理后才设置 `TRUST_PROXY=true`。`GET /healthz` 只检查进程存活；`GET /readyz` 只有在真实视觉识别和 Google Places 都配置后才返回 200，二者都不返回密钥。

服务端还在 `data/daily-budget.json` 持久化东京日期口径的应用级每日预算。视觉请求、Places Text Search 和 Place Details 默认各最多 90 次/日，低于当前供应商控制台 100 次硬配额并预留 10 次排障空间；缓存命中不会重复消耗 Places 应用预算。超限时返回 `429 DAILY_BUDGET_EXHAUSTED`，不会继续调用上游。可通过 `.env.example` 调低预算，但不应把应用上限设得高于供应商硬配额。

隐私最小化事件与数据源指标默认保留 30 天，每个 JSONL 文件同时限制为 50,000 行和 10 MB；服务首次写入和之后每 100 次写入会串行、原子裁剪过期、损坏、未来时间或超限记录。生产环境可通过 `.env.example` 中的留存变量进一步收紧，不能无限期积累试用行为日志。

## 测试

```bash
npm test
```

生产环境可运行 `npm start`，或使用仓库内的最小化 Docker 镜像。环境变量、健康检查和上线前核对项见 [docs/deployment.md](./docs/deployment.md)。

候选准确率评测需要先配置 Google Places key 并运行本地服务：

```bash
npm run eval:validate
npm run eval:candidates
npm run eval:decisions
npm run eval:platform-navigation
npm run metrics:summary
npm run pilot:gate
```

真实案例保存在 `eval/cases.json`。当前共有 33 个已确认案例，超过 30 例候选基线。`eval:decisions` 会在候选匹配后继续获取同一 Place ID 的详情，并检查推荐预约、闭店、同名分店冲突、官方不接受预约证据、发现页误升级和“预约成功”误导文案；报告写入 `eval/latest-decision-results.json`。该审计会产生真实 Places 及可选数据源调用，但不会修改人工审计记录。发布审计仍单独要求 30 个真实移动端完整流程，不能用候选命中、决策回归或单元测试替代。

`pilot:gate` 只计算新版本产生的真实产品流量，要求至少 20 次 live 输入、10 次有效反馈、分析完成率 ≥80%、行动率 ≥35%、有帮助比例 ≥60%。重复点击按一次分析去重；审计和无法归属到新分析运行的旧事件被排除。7 日内回访和可选的付费意愿分布（会考虑 / 看价格 / 不会 / 不确定）目前只报告，不作为通过条件。

小范围试运行的人员分配、输入组合、隐私边界和每日复核步骤见 [docs/pilot-runbook.md](./docs/pilot-runbook.md)。反馈只有在服务端确认接收后才显示提交成功；网络失败时表单会保留并允许重试。

## 当前边界

- 服务端读取用户提交的网页和餐厅官网时，会在每一跳校验 DNS，拒绝私网/保留地址，并把实际连接固定到已校验 IP；重定向最多 3 次且逐跳重新校验。
- HTML 响应按流读取；`Content-Length` 或实际读取量超过 512 KB 时立即中止并返回 `TOO_LARGE`，不会先把整页载入内存。
- 视觉模型输出还会经过独立的提示注入模式检查。店名、分店、地址等字段若含中/英/日文指令式文字，系统保留原线索但降为低置信度并强制人工确认；该检查不把截图文字当成可执行指令，也不替代候选与官方来源核验。
- 可用 `PILOT_ACCESS_CODE` 为封闭试点加一层共享访问码。未设置时行为不变；设置后截图、公开网页和餐厅 API 要求 `X-Pilot-Access`，并在限流或预算扣减前拒绝无效请求。访问码只保存在参与者当前浏览器，审计令牌仍是独立机制。
- 生产部署必须由可信反向代理提供 HTTPS，并在该代理确定性覆盖 `X-Forwarded-For` 时才启用 `TRUST_PROXY`。当前限流、缓存和每日预算是单实例设计；扩容前必须迁移到共享原子存储。未捕获进程错误会安全摘要后非零退出，由托管平台重启。

- 3 家餐厅为虚构演示数据，只在未配置 API key 时用于明确标注的交互演示；真实评测与发布门槛只计算 `eval/cases.json` 中经来源确认的案例。
- 未配置 API key 时，只有本次提供的 TikTok 截图能使用本地结构化示例完成解析。
- Qwen3.6-Flash 已使用用户提供的 TikTok 截图完成真实供应商联调；OpenAI fallback 仍只完成模拟响应测试。
- 前端已完成真实截图上传 → Qwen 识别 → 用户修正店名/地址 → Google Places 实时候选 → 用户确认 → 详情与行动建议的浏览器端验证。若一张截图明确出现多家餐厅，确认页会先列出餐厅让用户选择，不把作者账号、菜名或附近地标自动当成店名。
- 截图只有具体车站、没有地址或地区时，最近车站仍会显示为可编辑字段并进入 Places 查询；纯文本和待分析队列也保留该线索。真实无地址查询“ホームズパスタ 上野駅”已命中上野店，且不会把线路名误当作具体车站。
- 截图未识别出店名时会阻止候选搜索；低置信度或 fallback 结果要求用户勾选“已人工核对店名、分店和地址”，不能无提示继续。
- PNG/JPEG/WebP 截图会在服务端直接读取像素尺寸；短边不足 360px 或长边不足 640px 时，即使模型自报高置信度也会显示低分辨率警告并要求人工确认。WebP 的 VP8、VP8L 与 VP8X 三种封装均支持。该检查不会为了同一张低清图片额外调用备用模型。
- 上传选择器会在发送前拒绝 HEIC/HEIF、GIF、空文件和超过 8MB 的图片；桌面浏览器也可以直接把 PNG/JPEG/WebP 截图粘贴到餐厅线索输入框。
- 截图中的画面文字、帖子说法和作者观点分开显示。临时休业、闭店、搬迁和预约状态即使出现在截图里，也只作为未核验帖子线索，不会直接形成行动结论；确认具体门店后仍须由当前 Google Maps 状态或已核验官网复核。
- Google Places API (New) 已完成真实联调，Key 仅允许访问 Places API (New)；Text Search 与 Place Details 的每日硬配额均为 100 次。
- Hot Pepper 数据出现时，结果页会显示 Recruit 要求的 Hot Pepper Web Service 署名；真实 API Key 申请仍需邮箱验证和用户本人同意利用条款。
- 预约入口统一输出为 `reservationOptions`：当前识别已核验餐厅官网、Google Maps、电话、Hot Pepper、Tabelog、TableCheck、Rakuten Gurunavi、一休、OMAKASE、Pocket Concierge、TABLEALL、OpenTable、Reserve with Google、EPARK、AutoReserve、ヒトサラ、SAVOR JAPAN、Toreta、ebica、PayPay Gourmet、OZmall、Retty、byFood、Foodies Reserve、JPNEAZY、My Concierge Japan 和 JapanFoodTravel。未发现直接店铺链接时，Tabelog、TableCheck 与 Gurunavi 只提供明确标注的查找入口；普通 Google 搜索或 Maps URL 不会被误判成 Google 预约流程。
- 每个入口同时输出保守的 `capability`：官网核对、外部网站核对、线上预约流程、平台管理的预约/代订流程、排队取号、电话确认、平台店铺页、地图信息或仅查找。TableCheck、Toreta、ebica 等明确预约 URL 才会标记为线上预约；Hot Pepper 与 AutoReserve 的平台流程会提示确认方式待平台决定；AutoReserve 与 Pocket Concierge 的普通详情页不再直接视为可预约；EPARK 排队入口明确声明不等于订座。
- 平台提示按服务差异展示：Tabelog 系统使用费与请求预约状态、TableCheck/OMAKASE/一休的信用卡或取消条款、Pocket Concierge 在线结算、TABLEALL 预购席位/请求预约与预约费、Reserve with Google 的确认邮件边界、AutoReserve 代订及费用、EPARK 过号风险都必须在进入第三方页面后再次核对。
- 候选搜索保持 Google Text Search Pro 字段，不批量请求评分。用户可以对单个候选按需展开评分；该操作会请求一次 Place Details Enterprise，并在 60 秒内确认同一餐厅时复用缓存。评分只用于信息展示，不用于推断餐厅是否接受预约；应用不请求设备定位，也不伪造距离。
- 实时结果使用 evidence-gated 决策：闭店状态优先于第三方入口；只有明确直达预约流程时才输出“建议预约”；评分、评价数或平台店铺页不会被用来推断预约和排队规则。`decisionEvidence` 会附带结论、可信度、证据引用与判断限制。
- 临时休业结论只接受 Google Maps 状态，或店名与地址双重核验后的餐厅官网明确文字。真实 MKレストラン佐世保大塔店回归确认：官网和 Maps 均显示临时休业，即使官网仍保留 Hot Pepper 预约链接，主行动仍为核对官网状态，且恢复日期不会被猜测。
- 官网发现会在同一次受限 HTML 抓取中同时检查预约平台链接与少量高精度的“明确不接受预约”日文规则。后者可形成保守的现场到店建议，但不会推断实时有位或排队时间；若正文规则与直接预约入口冲突，则降级为“未知”并要求人工核对。
- 官网预约规则同时支持少量高精度的条件识别：仅平日、仅周末/节假日、仅晚餐、午餐不可预约，以及达到指定人数才接受预约。条件规则会与预约入口同时展示，但不会根据用户计划自行断言条件已满足；没有已核验入口时仍保持“信息不足”并建议打开官网或电话确认。
- Google Places 返回的平台托管页（例如 `gorp.jp`）会保持为平台店铺页；未知域名默认只称“Google Maps 所列网站”并使用中置信度。只有按店名与地址双重核验的来源才能升级为餐厅官网，避免把社交主页、Linktree、酒店目录或第三方平台误标成品牌官网。
- 输入或截图中的具体地址与当前 Maps 地址不一致时会标记高风险；未解决时预约链接不能成为主操作。若当前官网与 Maps 已共同核验迁址，则展示旧址警告并只使用现址对应的预约入口。
- 候选确认页允许用户逐家选择“不是这家”、恢复已排除候选，或在全部不确定时返回修改线索；排除动作不会触发餐厅详情请求，也不会被当成用户确认。
- 候选页显示重排后的名次、候选总数、Google Maps 营业状态和匹配原因；确认事件只记录候选数量与选择名次，不记录候选店名。
- 页脚提供“隐私与数据”和“服务条款”两个独立页面；条款明确当前原型不是预约代理、打开入口不代表预约成立，并提示第三方费用、取消条件与过敏信息必须再次核对。
- 电话助手支持标准版、简短版和“日语不熟练”三档，并按决策区分“询问预约”与“确认营业及现场等候”两类话术；第三档先请求对方慢速表达，再用短句逐项说明日期、时间和人数。计划中的 ISO 日期与时间会转换为自然日语（例如 `2026-08-01 / 19:30` → `8月1日 / 19時30分`）。用户可以在本机设置可选预约姓名，填写后自动加入三种预约话术，未填写时自然省略姓名句。复制按钮始终复制当前显示的日语版本。
- 对已按店名和地址核验的品牌官网，系统会保守提取带“电话/TEL”标签的公开号码；若与 Google Maps 或平台转接号码不同，结果页会显示来源冲突并优先使用品牌官网号码。
- 对已核验餐厅官网直接链接的 Instagram 账号，结果页会显示“官方 Instagram”入口；系统只保存并展示账号 URL，不自动读取或摘要 Instagram 帖子。未核验网站中的社交链接不会升级为官方来源。
- 已核验官方门店页中的明确“仅限现金、儿童限制、席位费、全席禁烟、着装要求”会作为到店注意事项展示并链接原文；未核验网页或含糊描述不会形成这些结论。
- 已核验官方门店页若明确写出整理券、App/网页取号、到店登记姓名或现场按顺序排队，结果页会单独展示官网原文和对应下一步。排队方式不会被用来推断预约一定关闭、实时有位或具体等待时间；只有官网同时明确写明不接受预约时，才形成保守的现场到店建议。
- 当前真实候选集包含 33 个案例，其中 30 个地域基线由品牌、政府或官方观光来源确认，覆盖北海道、东北、关东、甲信越、北陆、东海、关西、中国、四国、九州与冲绳；最新 Google Places 地域基线为 Top-1 30/30、Top-3 30/30。33/33 案例已通过“候选 → 同一 Place ID 详情 → 决策安全”真实 API 回归；发布门槛还会要求该报告覆盖全部当前确认案例、逐项通过且生成时间不超过 7 天。发布要求的完整人工移动端审计为 30/30（全部确认案例中为 30/33），风险矩阵为 28/30，因此整体发布门槛仍保持失败。
- 日本地址匹配会归一化全角数字、Unicode 连字符以及数字形式的丁目/番/号，因此仅提供 `歌舞伎町1-25` 这类部分地址时也能与 Maps 的 `歌舞伎町1丁目25-3` 形成可解释匹配；仍必须由用户确认具体分店。
- 想去清单支持计划日期、时间、人数与“需预约 / 已预约 / 可现场去 / 信息不足 / 暂不推荐”状态，并按行动状态及最近的未来日期优先排列。实时餐厅只持久化 Place ID、用户自己的线索和计划字段，重新打开时刷新第三方详情；旧版书签会自动迁移。
- 普通文字会在搜索前拆分餐厅线索与计划日期、时间、人数。单独的 TikTok、Instagram、小红书或 X 链接只标记平台来源，不声称已经读取帖子内容；用户需要补充截图、正文或店名。链接旁的正文只作为用户提供的线索使用。
- PWA 系统分享入口仅接收标题、文字和链接并预填首页，不会自动提交，也不会因分享来源而绕过社交链接、普通网页或预约平台 URL 的既有安全分类。分享查询参数在页面读取后立即从地址栏和当前历史项中移除。
- PWA 离线缓存仅包含静态应用外壳；Service Worker 明确绕过 `/api`、非本站请求和所有非白名单资源，不持久化餐厅详情、预约入口或第三方响应。离线状态下新的分析会被前端阻止并提示联网。
- 用户主动提交普通公开网页时，服务器会先做 DNS/私网/重定向检查，最多读取 512KB HTML，只提取页面标题和 Restaurant JSON-LD。网页内容始终作为待确认线索，不作为官方事实；社交平台登录页仍不会被自动读取。
- Tabelog、Hot Pepper、TableCheck、Gurunavi、OMAKASE、TABLEALL 等已知预约平台 URL 会先按店铺页/明确预约路径分类，不进入普通网页提取器，也不抓取平台正文、库存或结算信息。仅粘贴平台链接时会要求补充店名、地址或截图；链接旁有文字时只使用用户提供的文字匹配餐厅。餐厅确认后，该 URL 可以作为“用户提供、未独立核验”的低可信入口显示，但不能成为主操作，也不能覆盖餐厅官网发现的同平台入口。
- Google Maps 所列的第三方平台链接同样不能仅凭 URL 成为主操作；推荐顺序先看来源是否已核验，再看是否为明确预约路径。AutoReserve 仅在已核验餐厅官网明确提供该入口时才具备推荐资格。
- 日期、时段和人数会进入最终决策的计划提醒：周末、晚餐和多人只触发提前核对、套餐、桌型或押金提示，不会被用来凭空断言热门、有位或必须预约。
- 中文用户输入常见品牌别称时，会通过受控别名表展开为日文正式名，并单独保留原始中文名称；当前覆盖一蘭、一風堂、鳥貴族、すしざんまい、かに道楽、利久、矢場とん和串かつだるま。别名只改善搜索，不绕过分店确认。
- 页脚“隐私与数据”展示当前浏览器保存的计划数量、第三方请求的数据边界和服务运行记录范围，并提供两步确认的一键本机删除。该操作会清除本机计划、待分析队列、最近分析与设置，不会误称已删除第三方供应商或平台的数据。
- Google Places 与 Hot Pepper 适配层已完成；未配置相应 key 时界面会明确降级为演示模式。
- 普通 Hot Pepper 店铺页只作为待核对的外部页面；只有 URL 明确进入预约路径时才标记为平台预约流程，而且仍区分即时预约和请求预约，不会被表述成已经预约成功。
- 清单保存在当前浏览器的 localStorage，尚无账号同步。
- 最近分析在本机最多保留 10 条；实时餐厅只保存 Place ID、用户自己的线索和计划字段，打开历史时刷新详情，不保存完整 Places 快照或截图。
- 结果页支持系统分享；不支持 Web Share API 时复制一段隐私最小化的行动摘要。分享内容不包含电话号码或原始输入，并始终提示预约以餐厅或平台最终确认为准。
- 一张截图识别出多家餐厅时，用户可以把其余餐厅加入本机待分析队列，随后逐家确认真实店铺；队列最多 30 家，只保存餐厅名、分店和位置线索，不保存截图、帖子正文或互动数字，完成分析后自动移除。
- 待分析页支持旅行前批量粘贴，每行一家，或使用“店名｜分店｜地区/地址”格式；批量导入只建立本机线索队列，不会立即并发调用视觉、Places 或 Hot Pepper API。
