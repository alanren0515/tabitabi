# TabiTabi 产品审核与落地计划

审阅日期：2026-09-08
审阅范围：当前 `main`、已部署的 `https://tabitabi-jp.fly.dev`、首次访问流程、截图/店名输入、候选确认、结果页、设置页、PWA 与发布证据。
审阅方式：代码与产品文档审阅、真实 in-app Browser 流程检查、现有自动化测试与 provider-free smoke 证据；另行请求 Astra（`gpt-6-astra`，high reasoning）进行独立只读复核。

## 1. 先给结论

TabiTabi 的核心方向是合理的：它不是“替用户自动预约”的 AI，而是把 SNS 中的截图、店名或链接，转换成“确认真实门店 → 核对可信信息 → 选择下一步行动”。证据边界、用户确认、日文原文优先、隐私处理和不冒充预约成功等原则，构成了可信的产品基础。

目前最大的问题不是功能不足，而是首次访问时的理解成本和页面层级：

1. 新用户需要先理解“这是一个封闭测试/邀请码入口”，再理解“我可以用它确认餐厅”，最后才看到真正的输入动作。价值展示和访问门槛的顺序容易让人犹豫。
2. 首页视觉上干净，但主任务没有被压缩成一个足够明确的动作。截图、店名、邀请码、语言说明、示例、隐私提示和底部导航同时出现，产品的“第一步”不够突出。
3. 结果页的信息可信度很高，但“示例警告、原文说明、行动卡、判断结果、冲突提醒、详情依据、来源、反馈”叠加后，容易从“下一步是什么”变成“先读完一份审计报告”。
4. 最近确认、想去清单、稍后确认、设置和运行信息都很有价值，但不应在第一次打开时与主任务拥有同等视觉权重。

因此建议做一次“减层级、强主任务、保留证据”的 P0/P1 调整，而不是重写架构或增加新的 AI 功能。

## 2. 当前已经做对的部分

- 产品边界清楚：不会把“打开预约入口”说成“预约成功”。
- 截图只用于确认餐厅；真实候选需要用户确认，避免自动选择错误分店。
- 候选页将“这是哪家店”与“接下来怎么做”分开，交互安全性较好。
- 结果页的主要行动会根据预约、电话、地图等动作动态变化，方向正确。
- 低可信度、信息冲突、来源和原文都可追溯，适合日本餐厅信息不稳定的场景。
- 日语原文优先、浏览器翻译仅作为辅助、隐私与 API 状态放在可解释位置，信任设计完整。
- 移动端已有触控尺寸、单列布局、截图预览和离线/恢复状态；最新提交已改善首页层级和结果动作文案。
- 当前部署的静态资源与本地 HEAD 一致；provider-free smoke、健康检查、readiness、能力接口和内部路径保护均已验证。

## 3. 首次访问体验判断

### 对完全不了解项目的用户

结论：**可以用，但不够“马上会用”**。用户大概率能看懂“上传截图或输入店名”，但可能在以下位置停顿：

- 为什么一打开先要求邀请码？这是产品本体还是测试后台？
- 我上传的是 SNS 截图，还是餐厅照片？
- “确认餐厅”之后会得到什么？是地图、营业时间、预约入口，还是直接完成预约？
- 结果页中的“可信度”“判断理由”“来源”是否必须全部阅读？
- “最近确认 / 想去 / 稍后确认 / 设置”分别有什么区别？

### 首页

首页不是信息过少，而是**主任务旁边放了太多二级信息**。建议保留一个清晰的价值句和两个输入入口：

> 把 SNS 里的截图或店名，确认成真实餐厅，再决定预约、电话或到店。

第一屏应让用户在 5 秒内回答三个问题：

1. 我能放什么？截图、店名或链接。
2. 我会得到什么？真实分店、当前状态和下一步入口。
3. 会不会替我预约？不会，只会带我到可信入口核对。

邀请码仍然可以保留在 pilot 模式，但应被解释为“测试访问条件”，不能成为用户对产品价值的第一印象。示例体验应更容易被发现，最好与访问说明并列，而不是隐藏在首页下方的折叠区。

### 候选页

当前“确认这家 / 不是这家 / 修改线索”是正确的决策结构。需要避免候选卡上过早出现过多评分、来源和匹配理由；候选页的首要任务是确认分店，证据可以继续用折叠区承载。

### 结果页

当前行动入口清楚，是最重要的优点。建议把首屏固定为：

1. 餐厅名称与地点；
2. 一句“建议动作”；
3. 一个主按钮；
4. 一句不可忽略但短的限制说明。

判断理由、详细来源、营业时间、预约规则和反馈应保持可访问，但通过渐进披露降为第二层。示例提示和“语言/原文提示”如果表达的是同一限制，应合并，避免连续出现多个黄色说明块。

### 设置页

普通用户真正需要的是语言、默认人数、是否保存最近确认和当前测试访问码。API 状态、模型名、调用额度、provider 运行情况属于运行信息，当前折叠设计是对的；应继续避免把它们变成普通用户的必读内容。

## 4. 需要改进或合并的点

### P0：首次任务与价值理解

1. **重写首页第一屏信息架构**
   - 保留一个主标题、一个价值说明、截图主入口、店名/链接次入口。
   - 在输入区附近增加一句短的结果承诺：`真实分店 → 核对当前信息 → 预约 / 电话 / 地图`。
   - 明确写出 `不会自动预约，也不会把预约入口当成预约成功`，但不要把安全说明写成大段正文。
   - 将邀请码说明改成低干扰的 pilot 状态区；错误时仍要高可见。
   - 将“查看示例”提升为与输入入口同级的轻量次级动作，允许新用户先理解产品。

2. **让 CTA 只表达一个下一步**
   - 无输入时显示具体提示，而不是让用户猜为什么按钮不可用。
   - 有截图时 CTA 表达“确认截图中的餐厅”；有店名时表达“确认这家餐厅”；两者都有时表达“确认餐厅”。
   - 不改变当前截图/店名输入的语义，不引入自动提交。

3. **减少首次访问的导航噪声**
   - 移动端保留语言和一个必要的入口；最近、想去、设置可以降低视觉权重或收进轻量菜单。
   - 桌面端仍可保留快捷入口，但必须不与主任务竞争。
   - “最近确认”“想去”“稍后确认”在文案上明确区分：历史、计划、未完成输入。

### P1：结果页和运行信息的层级

Astra 的独立代码审阅还发现了几项应与信息架构调整一起处理的具体风险。这些是代码证据或明确的布局证据，落地前仍需实现模型用 fixture/浏览器复现：

- 结果页目前先渲染主行动，冲突、预约条件、费用和到店限制更靠后；高风险限制必须在行动前或行动旁出现。
- 候选卡把 `OPERATIONAL` 显示成“营业中”，但它只代表门店仍在运营，不等于此刻 `openNow` 为真；三语需要区分“仍在营业/未关闭”和“现在营业”。
- “返回修改”路径可能调用清空搜索状态；修改一个字或截图线索时，应保留当前草稿、图片和已完成的识别，不应与“开始新的搜索”共用行为。
- 文本/截图修正后的字段没有始终回写为下一次搜索和恢复的单一事实来源；失败重试、返回或切换语言时可能恢复旧值，且截图重试可能重复识别。
- 受保护请求的 pilot access 拒绝恢复需要统一；截图识别、截图审阅、候选搜索和详情阶段都应清除失效码、保留输入并聚焦重输。
- 820px 左右的中等宽度存在横向溢出风险；不能只验证手机和宽桌面，必须覆盖 320、390、430、760、768、820、1024px。
- 上传前的隐私提示没有就近说明“何时发送、会发送给谁、不要上传 DM/通知等私人内容”；隐私页应先讲数据流，再讲本机计数和管理。
- “建议预约”保存后被压成“需要预约”，容易把系统建议强化成事实；“已预约”也必须明确是用户自行记录，不是系统确认。

这些问题的优先级高于继续增加功能，但不等于已确认线上存在需要停服的 P0 故障。当前应保持邀请制，并在扩大 pilot 前完成验证。

4. **把结果页变成“行动优先，证据随后”**
   - 主卡：餐厅、地点、当前状态、主动作。
   - 次卡：可信度与一句判断摘要。
   - 合并或去重示例警告、语言说明和冲突说明；冲突必须仍然靠近受影响的行动。
   - “其他操作”只放电话、地图、保存、分享等辅助操作。
   - 详细信息、来源、预约规则和反馈继续保留，但默认折叠或下移。

5. **降低技术运行信息的产品权重**
   - 设置页继续折叠 API 状态和今日额度。
   - 用户可见文案优先说“当前可用功能”，模型名和配额作为展开后的诊断信息。
   - 不在首页重复显示 API、模型、额度、缓存、provider 等内容。

6. **统一“可信度”语言**
   - 用户需要知道的是“为什么可以相信 / 还需要核对什么”，而不是模型分数。
   - 保留高/中/低作为辅助标签，但主文案使用行动含义：`可以继续核对`、`请先确认分店`、`信息不足，暂不建议行动`。
   - 所有“预约”文案继续严格区分预约入口、预约申请、候位和预约已成立。

### P2：验证产品价值，而非继续堆功能

7. 用真实 pilot 反馈验证：首次理解时间、首次输入选择、候选确认率、主行动点击率、返回修改率、结果有帮助率、真实预约/电话/到店后的准确性。
8. 在这些指标稳定前，不扩展原生 Share Extension、账户体系、全量 SNS 抓取、自动预约或 AI 自动翻译。
9. 继续保持 PWA 和当前证据链架构；先优化用户理解和行动闭环。

## 6. 明确不要做的事

- 不要把产品改成自动预约或“AI 替你完成预约”。
- 不要移除用户确认真实分店的步骤。
- 不要用更大的说明文替代层级优化。
- 不要因为首页想更“丰富”而增加更多卡片、评分、模型信息或社交入口。
- 不要在没有 pilot 证据的情况下引入原生 App、账户系统、全量社交平台抓取或自动翻译 API。
- 不要覆盖用户已有工作区修改，不要重置 Git，不要在本计划阶段部署。

## 7. 完成定义

实现模型只有在以下条件都满足后，才能报告完成：

- 首次访问者能在 5 秒内说出“我可以上传什么、会得到什么、是否会自动预约”。
- 首页只有一个清晰主任务，pilot gate 不再遮蔽产品价值。
- 结果页首屏能看懂“这家店是谁、下一步是什么、还要核对什么”。
- 证据、来源、冲突和原文仍可访问，且预约边界没有被弱化。
- JA/EN/zh-CN 文案和 aria-label 没有回退到错误语言或旧术语。
- 360px、390px、430px 视口无横向溢出，主要控件满足触控尺寸和键盘焦点要求。
- `npm test` 全部通过；相关 in-app Browser 流程有截图/AX 或可复现步骤证据。
- 未引入新的付费调用、生产数据变更、未授权部署或新基础设施。
- 最终报告分开列出：已验证、推断、未验证、仍需真实 pilot 数据的事项。
