# TabiTabi 首版产品与架构决策

## 结论

首版做移动优先的响应式 Web/PWA，不直接做原生 App。

### 目标用户与 SNS 边界

TabiTabi 的核心用户是在日本生活、用日语消费餐饮信息的一般用户，不以赴日游客或在日华人为主要人群。默认市场是日本，默认产品语言应为日语；中文和英文作为后续可选语言，而不是默认信息架构。

SNS 按“日本用户发现餐厅的作用”分层，而不是只按总利用率排序。总务省令和 6 年度调查显示，全年代利用率为 LINE 91.1%、YouTube 80.8%、Instagram 52.6%、X 43.3%、TikTok 33.2%；但餐厅发现调查中，Instagram、YouTube、TikTok 更直接影响选店。因此产品优先级为：

1. **P0 餐厅发现：Instagram、TikTok**。优先验证短视频、图文帖子和完整截图中的店名、分店、车站与帖子观点分离。
2. **P1 补充发现：YouTube Shorts、X**。YouTube Shorts 是重要的视频发现补充；X 更适合识别开业、临时休业、迁址等时效性声明，但所有运营状态仍需当前官方来源复核。
3. **P1 转发入口：LINE**。LINE 主要承接朋友间转发的链接或文字，不把聊天对象、群名或聊天内容当成餐厅事实。
4. **P2 补充来源：Threads、Lemon8**。复用通用截图和公开网页线索能力，在真实试点中观察是否值得独立优化。
5. **P3 兼容来源：Facebook、小红书**。保留通用截图和链接识别；小红书用于跨语言与旧帖风险回归，但不代表核心用户画像，也不决定默认界面或产品路线。

数据参考：[总务省令和 6 年度信息通信媒体利用调查](https://www.soumu.go.jp/menu_news/s-news/01iicp01_02000125.html)、[2025 年 Z 世代餐厅信息收集调查](https://prtimes.jp/main/html/rd/p/000000011.000058070.html)。平台优先级仍需用本产品的真实输入来源和行动率持续校准。

Google Maps、食べログ、Hot Pepper、ぐるなび与餐厅官网不是 SNS 发现入口，而是门店身份、当前状态和预约行动的核验层。

原因：当前最大风险是用户是否真的需要“餐厅线索 → 可执行下一步”，不是系统能否进入 App Store。Web 能直接承接社交平台复制链接与截图上传，迭代、分发和埋点更快，也能先验证完整闭环。原生端最有价值的能力是 Share Extension；等 Web MVP 证明用户反复使用后，再用 iOS/Android 外壳或 React Native 补分享入口、通知与日历。

### iOS 分享入口的测量限制

当前 Web/PWA 的 Web Share Target 不能让 iOS Safari 或安装到主屏幕的 Web App 注册为系统图片分享目标。iPhone 用户仍可手动截图后上传，或复制文字/链接回到产品，但无法从 TikTok、Instagram、YouTube、X 等 App 的系统分享面板直接把图片交给本产品。日本市场 iPhone 占比较高，因此 pilot 中“从 SNS 分享进入产品”的转化会被系统性压低，不能直接解读为用户没有分享需求；结果页向外分享是另一项指标，也不能代替该入口测量。

原生壳的 Share Extension 仍排在“Web 闭环验证通过后”，本轮不实施。只有候选识别、行动率、帮助度和复用意愿达到门槛后，才用原生入口验证系统分享带来的增量。

## 首个原型的纵向切片

1. 输入店名、帖子文字或截图文件名。
2. 未配置 Places 时通过本地可测试规则匹配 3 家虚构演示餐厅；配置后使用真实 Google Places 候选。
3. 用户确认候选，避免低置信度时自动下结论。
4. 展示预约建议、行动 CTA、冲突提示、来源与置信度。
5. 提供日语电话话术，并把餐厅保存到浏览器本地清单；其他语言作为后续可选辅助，不进入首版默认流程。

## 截图理解阶段

截图不再只做 OCR 文本拼接，而是先拆成四组结构化数据；一张图可保留最多 6 家明确可见餐厅，并由用户选择要继续核对的一家：

1. 餐厅匹配字段：店名、分店、地址、区域、料理和预算。
2. 社交来源字段：平台和作者账号。
3. 帖子声明：开业背景、评价、推荐理由；默认不是官方事实。
4. 互动字段：点赞、评论、收藏和分享；永远不直接参与预约或排队判断。

浏览器把图片作为 data URL 发送到本地服务端，服务端再调用视觉模型。API key 不进入客户端，截图不落盘。模型输出受严格 JSON Schema 约束；提取完成后，用户必须先审阅店名、分店和地址，才能进入候选匹配。

本次用户提供的 TikTok 截图内置了一份本地示例解析，因此没有 API key 时也可验证交互。界面会明确显示“本地示例”，不会伪装成实时 AI 结果。

当前版本已经接入 Qwen 视觉理解、Google Places 和可选 Hot Pepper；GPT-5.4 mini 仅在配置 OpenAI Key 后作为质量兜底。虚构数据只保留为未配置 API 时明确标注的交互演示，不进入真实评估或发布门槛。

## 建议的生产架构

- 前端：响应式 Web/PWA；后续增加系统分享入口。
- API：单体服务起步，提供 analyze、candidate confirmation、saved list、feedback。
- 异步任务：只有当真实 OCR/搜索耗时超过请求窗口时再加入队列。
- 数据：PostgreSQL 保存用户清单、内部分析与审计；对象存储仅临时保存截图并设置自动删除。
- 数据源：Google Places 官方 API 用于地点候选，Hot Pepper 官方 API 用于店铺信息补充，官网/官方 SNS 优先作为预约规则证据；Hot Pepper API 命中和普通平台店铺页本身都不证明可预约，食べログ首版只做合规链接跳转。
- AI：只负责结构化实体提取与基于证据的解释，不能自行生成来源、预约入口或等待时间。
- 审计：每条结论绑定 source URL、retrieved_at、字段级置信度与冲突状态。

## 真实餐厅核对实现

当前版本已经实现以下服务端链路：

1. `POST /api/restaurants/search`
   - 使用 Places Text Search。
   - 只请求候选阶段需要的 Place ID、名称、地址、类型、营业状态、地图链接和坐标。
   - 不在候选搜索中批量请求高计费评分字段。用户主动展开某一候选评分时才请求该 Place ID 的详情，并与随后确认流程共用 60 秒短缓存。
   - 最多返回 3 个候选，并附带店名、分店和地址匹配原因。
2. `POST /api/restaurants/details`
   - 只在用户确认候选后调用 Place Details。
   - 获取电话、营业时间、官网和营业状态。
   - Hot Pepper 作为可选补充源；失败时不影响 Google 详情结果。
3. 确定性决策引擎
   - 每个字段生成独立证据记录，包括来源、URL、查询时间和置信度。
   - 没有明确预约证据时，结果始终保持“信息不足”，不会根据评分或互动量猜测。
   - 官网明确的有限预约规则（仅平日、仅周末/节假日、仅晚餐、午餐不可预约、指定人数起）单独展示，不与“完全不接受预约”混淆，也不根据计划日期自动判定适用。
   - 排队规则只接受已核验餐厅官网的明确文字，当前识别整理券、App/网页取号、到店登记姓名和现场顺序排队；它与预约状态分开判断，且不估算等待分钟数。
4. 合规缓存边界
   - 实时第三方响应只保留在当前页面内存。
   - 想去清单只长期保存 Place ID、用户自己的线索和状态。
   - 重新打开已保存餐厅时按 Place ID 刷新详情。
5. 最小事件记录
   - 记录输入类型、识别成功、候选确认、分析完成、预约/电话/话术行动、保存、来源冲突和用户主动提交的结构化反馈；不记录原始截图或搜索文字。
   - 不记录截图、原始帖子文字、店铺详情快照或用户个人信息。
6. 多来源冲突
   - Hot Pepper 必须至少通过店名匹配，不能只因地址相同就认定为同一家店。
   - Google Maps 与 Hot Pepper 地址不一致时标记高风险，提示可能错配分店。
   - 用户截图/文字中的具体门牌与当前 Maps 地址不一致时，先阻止直接预约；只有店名与现址双重核验的官方门店页才能消解迁址冲突。
   - Hot Pepper 定休日与 Google Maps 对应星期营业信息矛盾时标记营业时间冲突。
   - 任一高风险冲突都会把结果置信度降为低。

## 上线前的停止条件

如果没有可合法使用的餐厅识别与预约数据源，或 20 个真实案例中正确店铺确认率低于 70%，不要扩建原生 App、批量规划或自动电话功能；先回到人工辅助流程修正输入与匹配。

## 首轮验证

- 找 10–15 位以日语使用 SNS 和餐厅服务的日本国内用户，收集 20–50 个真实餐厅线索；游客和中文用户只作为补充样本。
- 记录输入类型、正确候选是否出现在前三、用户是否点击行动按钮、建议是否有帮助。
- 首轮门槛：Top-3 识别率 ≥70%，分析完成率 ≥80%，行动点击率 ≥35%，有帮助比例 ≥60%。
- 每个严重错误都必须能追溯到错误来源、过期字段或推理规则，不能只改文案掩盖。
